# Fix: Expand INDIC_RE to cover all supported Indic scripts

## Problem

`INDIC_RE = /[\u0900-\u097F\u0C00-\u0C7F]/` only matches Devanagari (U+0900–U+097F) and Telugu (U+0C00–U+0C7F). Pure Malayalam, Gujarati, Bengali, and Punjabi PDFs fail the extraction validation and throw a 400 error, even though those languages are in `VALID_LANGUAGES`.

## Scope

Two files contain the same narrow regex. Both must be updated:

| File | Line | Current | Fix |
|---|---|---|---|
| `server/src/routes/documentRoutes.js` | 12 | `/[\u0900-\u097F\u0C00-\u0C7F]/` | `/[\u0900-\u0D7F]/` |
| `server/src/services/textProcessor.js` | 29 | `/[\u0900-\u097F\u0C00-\u0C7F]/` | `/[\u0900-\u0D7F]/` |

## Unicode coverage

`U+0900–U+0D7F` is the continuous block covering all standard Indic scripts used by the platform:

| Range | Script | Language codes |
|---|---|---|
| U+0900–U+097F | Devanagari | hi-IN |
| U+0980–U+09FF | Bengali | bn-IN |
| U+0A00–U+0A7F | Gurmukhi | pa-IN |
| U+0A80–U+0AFF | Gujarati | gu-IN |
| U+0B00–U+0B7F | Odia | — (not in VALID_LANGUAGES) |
| U+0B80–U+0BFF | Tamil | ta-IN |
| U+0C00–U+0C7F | Telugu | te-IN |
| U+0C80–U+0CFF | Kannada | kn-IN |
| U+0D00–U+0D7F | Malayalam | ml-IN |

All supported `VALID_LANGUAGES` codes map to scripts within this range. No false-positive risk from non-Indic scripts.

## Implementation

### Step 1 — `documentRoutes.js:12`

Replace:
```js
const INDIC_RE = /[\u0900-\u097F\u0C00-\u0C7F]/;
```
With:
```js
const INDIC_RE = /[\u0900-\u0D7F]/;
```

### Step 2 — `textProcessor.js:29`

Replace:
```js
if (/[\u0900-\u097F\u0C00-\u0C7F]/.test(text)) return text;
```
With:
```js
if (/[\u0900-\u0D7F]/.test(text)) return text;
```

### Step 3 — Syntax check

```
node --check server/src/routes/documentRoutes.js
node --check server/src/services/textProcessor.js
```

## Risks

- **None.** The change is a pure regex character-class expansion. No logic changes, no new dependencies, no schema changes.
- `/[\u0900-\u0D7F]/` is a subset of the broader UAX #32 Indic script range; it precisely covers all scripts we support and no others that would cause false positives in our context.
- `INDIC_LANG_CODES` in `textProcessor.js:3` (`['hi', 'te', 'ta', 'kn']`) is a separate issue — it limits which languages get translated. That is out of scope for this task; fixing it would require additional changes to `GNANI_LOCALE_TO_ISO` and the translation flow.

## Validation

- Upload a Malayalam PDF with `?language=ml-IN` → should succeed (no 400 from INDIC_RE guard).
- Upload a Gujarati PDF with `?language=gu-IN` → same.
- Upload a Bengali PDF with `?language=bn-IN` → same.
- Upload a Hindi PDF with `?language=hi-IN` → still works (Devanagari is within range).
- Upload an English PDF with `?language=en-IN` → still works (no Indic chars, language is en-IN so guard is skipped).
- `node --check` on both files passes.
